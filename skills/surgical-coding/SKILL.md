# 精准简洁编码

用解决当前问题所需的最小改动达成可验证目标。管理困惑，而不是隐藏困惑；管理复杂度，而不是把少写代码等同于好代码。

## 0. 先选择任务强度

- **明确小改动**：拼写、单行修复、已有模式内的局部变更直接完成并做相应检查。
- **普通功能或修复**：确认输入、输出、边界和验收，再实现最小差异。
- **高风险或长程任务**：补充目标、影响面、预算、回退和停止条件，分步验证。
- 只有会改变方向、成本、风险或验收的歧义才展开；已明确且低风险的细节自主决定。

## 1. 管理假设、歧义与矛盾

编码前区分：

- **事实**：代码、运行结果、文档或用户已经确认的内容。
- **假设**：为了继续推进而暂时采用、但尚未证实的解释。
- **决策**：在多个可行方案中实际选择的路径及其理由。

执行规则：

1. 写出影响实现的关键假设，不把所有内心推理都倒出来。
2. 多种解释会产生不同产物或验收时，列出差异；能低风险验证时先用证据排除。
3. 用户目标、代码行为和项目约定互相矛盾时明确指出，不静默折中或选择性忽略。
4. 目标、输入、范围或成功标准不清时，指出具体缺口；无法合理推进再询问。
5. 有更简单、更安全或更符合既有约定的方案时直接提出，说明收益、代价和风险。
6. 用户确认方向后停止重复争论，把决策落实到实现与验证。

## 2. 控制复杂度预算

优先复用项目已有且经过验证的模式，再考虑新增代码。每新增一个模块、状态、配置项、抽象层或依赖，都要能回答：

- 当前哪个真实需求要求它存在？
- 它替代或删除了什么复杂度？
- 不加入它会具体阻塞什么？
- 后续需求出现时能否再演进，而不必现在预付成本？

遵守以下边界：

- 不为单次使用创建通用框架，不添加未要求的功能、配置和理论扩展点。
- 不在同一改动中同时换架构、换风格和换行为。
- 不为内部契约已保证的不可能分支堆叠防御；网络、用户输入、文件和公开导出等真实边界必须校验。
- 发现更小实现时主动删减自己的冗余代码，但不以极简为名牺牲正确性、可读性或必要防护。
- 需求只出现一次时先保留直接实现；出现真实重复后再提取抽象。

## 3. 保持外科手术式差异

修改前建立最小上下文：相关调用链、既有风格、当前行为和验证入口。修改时：

- 只触碰与目标或验收直接相关的代码、测试和文档。
- 不重构没坏的部分，不顺手修改相邻注释、格式、命名、类型或引号风格。
- 不删除或改写自己尚未理解的既有逻辑与注释；需要变更时先补足证据。
- 发现无关缺陷、死代码或技术债时单独记录，不混入当前修复。
- 清理本次改动造成的无用导入、变量、函数和文件；保留原先就存在的无关内容。
- 避免全文件重写来表达局部修改，保留无需变化的字节与结构。

完成后逐块审查差异：每一处新增、删除和移动都应能映射到目标、必要兼容或验证要求，否则撤回或单独说明。

## 4. 将目标转成验证闭环

把模糊任务改写成可观察结果：

| 任务 | 可验证目标 |
| --- | --- |
| 修复 bug | 先让回归用例因原原因失败，再验证修复后通过 |
| 添加校验 | 定义有效、无效和边界输入，验证接受、拒绝及副作用 |
| 重构模块 | 重构前后运行同一组行为检查，外部契约保持不变 |
| 优化性能 | 固定输入、环境和测量方法，先记录基线再比较 |
| 提升可靠性 | 明确失败类型、降级行为、恢复条件和运行证据 |

多步任务为每一步绑定检查：

```text
1. [最小动作] → 验证：[能区分成败的检查]
2. [最小动作] → 验证：[相关回归]
3. [回到真实流程] → 验证：[原始场景与交付产物]
```

按风险选择验证层级：

1. **目标检查**：复现用例、静态校验或最小行为测试。
2. **邻近回归**：同一模块和共享调用方测试。
3. **真实流程**：原失败命令、端到端路径或实际产物核对。
4. **差异审查**：确认没有无关改动、隐藏失败和未交代的风险。

最小测试通过不等于真实流程已经修复。测试未运行、被跳过或环境不满足时，明确标注，不写成通过。

## 5. 处理失败与停止

- 失败后先保存错误、输入和现场状态，再改变一个关键变量。
- 不机械重复同一失败命令，不通过删除断言、降低阈值或隐藏输出制造成功。
- 临时绕路只用于验证假设，返回主线前重新验证正式路径。
- 达到预算或停止条件时，交付当前证据、最大卡点和下一步最有区分度的实验。
- 发现方向本身错误时及时说明并回退自己的无效改动，不继续堆补丁。

## 交付前自检

- 假设、矛盾、关键取舍和剩余不确定项是否已说明？
- 每项新增复杂度是否有当前需求支撑？
- 差异中是否有与请求无关的修改或本次产生的死代码？
- 原失败场景、相关回归和真实流程分别验证了吗？
- 交付说明是否区分已验证事实、实际改动、验证结果和剩余风险？
