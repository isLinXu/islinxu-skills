# 精准简洁编码场景示例

按任务风险选择流程，不机械增加提问、抽象或测试仪式。

## 1. 区分多种目标

**请求**：“优化这个多模态评测。”

不要同时改 Prompt、解析器和并发。先区分：

- 提高指标：检查模型、提示、答案解析与数据口径。
- 降低耗时：测量模型调用、图像处理和解析各阶段耗时。
- 提高稳定性：复跑并区分模型波动、解析错误和外部服务失败。

如果已经明确“不改变指标口径，只降低运行时间”，就保留评测契约并先测基线，不重复询问已有答案。

## 2. 暴露矛盾并给出取舍

**情况**：既要求“显著降低延迟”，又要求“模型、预处理、运行时和输出完全不变”。

不要挑选一方静默执行。先测量各阶段耗时，再说明：

- 不改模型与输出时，可优化I/O、缓存、批处理或调度，但收益受实测瓶颈限制。
- 量化、换后端或调整预处理可能收益更大，但会改变部分契约，需要单独验收。
- 在拿到基线前，不承诺“显著提升”的幅度。

取舍必须落到具体成本、风险和验证，而不是只说“需要权衡”。

## 3. 避免推测性抽象

**请求**：“给论文清单增加 CSV 导出。”

不创建策略注册表、导出插件、多格式框架和远程通知。先复用当前筛选结果，实现单一 CSV 导出，并覆盖：

- 当前筛选而非仅当前页。
- 空结果、中文、逗号和换行。
- URL 白名单与电子表格公式注入防护。

只有第二种真实格式需求出现后，再判断是否提取共同接口。

## 4. 控制修复范围

**请求**：“修复带版本号的 arXiv URL 被识别成两篇论文。”

采用最小闭环：

1. 添加 `2401.00001v1` 与 `2401.00001v2` 应生成同一 id 的失败用例。
2. 只调整版本号归一逻辑。
3. 运行论文身份测试和清单回归。
4. 回到原始重复清单确认去重结果。

不顺手重写标题 slug、调整所有文件格式或更换整个解析器。其他身份问题另列，不混入本次修复。

## 5. 保留尚未理解的代码

**情况**：修复导出精度时，发现相邻模块有一段看似冗余的坐标修正和旧注释。

不要因为“可能没用”就删除。先查找调用方、历史测试和不同后端的坐标约定；当前任务不需要变更时保留原样。确需修改时，构造能证明该分支行为的输入，并把兼容风险单独写入验收。

## 6. 将可靠性要求变成检查

**请求**：“让观测页更可靠。”

先转成可观察结果：

- 上游 429 时保留旧快照并显示 `stale`。
- 缺少 30 天前基线时显示未知，不显示 0。
- 首次采集只建立基线，不产生“新增全部”。
- 任一前端脚本语法错误都在部署前使 CI 失败。

逐项实现和验证后，再检查实际发布页面。单元测试全绿只能证明已覆盖的检查通过，不能证明部署一定更新。

## 7. 避免验证表演

**反例**：修改模型导出逻辑后，只运行一个辅助函数测试，就宣布端到端部署完成。

**正确闭环**：

1. 辅助函数测试验证目标分支。
2. 导出回归验证完整图能够生成。
3. 固定输入比较源模型与导出结果。
4. 在目标运行时执行实际推理。
5. 回到原部署命令核对最终产物和日志。

任何一层未运行都明确写出，不能把“没跑到”描述成“没问题”。

## 8. 简单任务不过度流程化

**请求**：“修正 README 中一个命令的拼写。”

确认命令原文和预期拼写后，只改对应位置并检查链接或命令文本。无需创建设计文档、任务矩阵、抽象模板或全仓库重构。

谨慎流程用于降低非平凡任务的昂贵错误，不应成为简单修改的负担。

## 交付差异审查

提交前按以下顺序自问：

- 哪些结论来自实际代码或运行证据？
- 哪些假设仍未验证，是否会影响使用？
- 哪个新增文件、状态、配置或抽象可以删掉？
- 哪个差异块与当前目标没有直接关系？
- 哪项检查证明了原问题，而不只是证明新测试能运行？
- 哪些真实流程、失败项和剩余风险还没有交代？
