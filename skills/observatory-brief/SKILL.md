# 观测简报

把 Model Observatory 的多个公开快照整理成一份可回查的行动简报。默认只读数据，不自动改任务、不根据热度替用户决定优先级。

## 1. 明确简报范围

- 日报优先回答：昨天哪里失败、哪些任务在推进、哪些新线索值得人工查看、哪些截止临近。
- 周报优先回答：任务状态迁移、清单增删、实体覆盖变化和需要回到主线的阻塞。
- 用户指定时间窗口、主题或项目时，只扩展对应筛选，不复制全部看板。
- 先读 [数据契约](references/data-contract.md)，区分当前快照、样本、历史、运行健康和项目指标。

## 2. 读取公开快照

联网生成：

```bash
python scripts/observatory_brief.py --days 30 --limit 5 --output brief.md
```

使用已下载快照离线复现：

```bash
python scripts/observatory_brief.py --data-dir /path/to/snapshots --at 2026-11-10T12:00:00Z --output brief.md
```

数据目录按文件名存放 `runs.json`、`tasks.json`、`awesome.json`、`entities.json`、`conferences.json`、`github.json`。单个来源失败时保留其他板块并明确列出，不将失败写成 0；全部失败才退出非零。

## 3. 按行动顺序组织简报

1. **先看采集健康**：最近运行的状态、失败和缺失步骤及其覆盖范围。
2. **再看当前工作**：`blocked`、`doing`、`review`、`proposal` 分开，已完成的任务不占行动列表。
3. **再看研究变化**：清单实测增删、停更与来源状态；新论文只从发布样本中选取并标明样本边界。
4. **再看项目与实体**：仓库活动只表示最近有推送，不代表价值；未登记清单是工作队列，不是质量评分。
5. **最后看投稿窗口**：只使用能归一到 UTC 的 paper 事件，投稿前仍回官网复核。

每个关键数字附来源文件和 `captured_at` 或运行记录时间。`stale`、`partial`、`unavailable`、未核对和范围外不得合并成“正常”或“失败”。

## 4. 形成下一步

- 将建议写成“检查 / 复核 / 继续 / 暂缓”，不写未经证据支持的“必须”。
- 引用任务 slug、论文条目 id、实体 slug 或会议事件 id，方便回到原看板。
- 样本不足时只说“样本中看到这些条目”，不声称遍历了全部新增。
- 不复制指标到任务卡或实体正文；需要最新值时重新读取对应来源。

## 5. 分级验证与差异审查

1. **目标检查**：用离线 fixture 验证状态、时间窗口、样本边界和缺失来源。
2. **邻近回归**：检查不同 schema、空列表、过去截止、非法 URL 和部分失败。
3. **真实流程**：对公开站点实际生成一次简报，抽查数字、slug 和链接能回到原快照。
4. **差异审查**：对比本次简报与上一版，区分真实数据变化、生成时间变化和筛选变化，不混入无关栏目或指标。

## 完成标准

简报中的每个关键结论都能回到公开 JSON 或运行记录。来源失败、样本截断、时间窗口和未运行检查必须明确显示。
